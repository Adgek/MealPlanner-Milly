# MM-26: a map of what the app can do, so planning the next ticket starts from one

**Ticket:** MM-26 — Use case diagrams: what's built, what's planned
**Landed:** 2026-11-26 · **Takes:** about five minutes, and it is all reading

Nothing changed about how the app behaves. What changed is that the question "what
can we actually do with this, and what is left?" now has one answer in the repo
instead of being reconstructed from the board's list of titles.

## How to see it

No stack needed for the map itself — it is Markdown.

1. Open **[`docs/use-cases.md`](../use-cases.md)**. On GitHub the eight diagrams
   render on the page; in an editor they are Mermaid code fences, which read fine as
   text. Nothing has to be installed either way.
2. Read **"How to read this"** first. Two things in it change how the rest reads:
   **built means a person can reach it** (not that the code exists), and **built does
   not mean right** — three merged paths have open fix tickets named on their row.
3. Then skim the seven group headings and stop at **[the gaps](../use-cases.md#the-gaps)**.

To check the map against the app rather than trusting it:

```sh
cp .env.example .env                                   # first time only
make up                                                # app, db and scheduler
docker compose exec app php artisan db:seed            # the sample recipes
docker compose exec app php artisan milly:plan --seed=42
docker compose exec app php artisan milly:groceries
docker compose exec app php artisan schedule:list
```

Then open <http://localhost:8000/plan> and <http://localhost:8000/recipes> next to
each other. That contrast — a planner that works, with no page to see it on — is the
thing the map is for.

## What you should see

- `milly:plan --seed=42` prints the next window and its nights — run on 26 Nov 2026
  that was `Shopping Sun 29 Nov — 3 nights: Mon 30 Nov to Wed 2 Dec`, with Beef
  Bulgogi, Quick Pasta and White Boy Tacos, each with a cook and a time budget. The
  dates move with the day you run it; the three dinners are what the seed fixes.
- `milly:groceries` prints 21 lines in six sections, including `Ground beef — 2 lb
  (Beef Bulgogi, White Boy Tacos)` — two 1 lb needs merged — and a `Check you have`
  section it tells you not to buy from.
- `schedule:list` says **"No scheduled tasks have been defined."** That is not a
  misconfiguration; it is group 6 of the map.
- `/plan` says **"Nothing planned yet. ARRIVES IN MM-8"** — while the window you
  just planned sits in the database.
- `/recipes` shows the five seeded recipes, each editable down to its ingredients.

## What's functional now

- **Before planning a ticket,** `docs/use-cases.md` says which use cases it touches,
  what state they are in, and which route, command or class already holds the logic —
  so a ticket is less likely to rebuild something the engine already does. MM-8 is
  the clearest case: re-roll, lock, hand-pick, override and tick all exist and are
  tested, and none of them has a surface.
- **The README's "What's here so far" is true again.** It had said the Plan and
  Settings pages were empty placeholders and that there were no household tables —
  five merged tickets out of date.
- **`AGENTS.md` sends you to the map** under "Read these first", and asks that a
  ticket changing what the household can do moves the tag in the same commit.
- **The gaps are written down** — three of them, all decisions rather than missing
  features, because the board turns out to cover `AppPlan.md` well. They are proposed
  in a comment on MM-26, not created: the household picks.

## What it still doesn't do

- **It is a snapshot, kept by hand.** Nothing fails if a ticket lands and the tag
  goes stale. The `AGENTS.md` rule is the only thing holding it true.
- **No merged ticket has a demo note to link to** (MM-1 to MM-23 all predate the
  convention), so every "built" row names a route or a command instead. This note is
  the first one in `docs/demos/`.
- **It does not create the tickets for the gaps it found** — out of scope on purpose.
- **MM-8's capabilities are tagged "in flight" from its branch, not from running it.**
  Its branch is in Needs Review and not merged, so the map describes `/plan` as the
  placeholder this branch actually has.
